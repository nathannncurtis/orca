ORCA

Building a fast, independent platform on a system you do not own

Nathan Curtis

October 2026Version 0.9Cite

Abstract

Many organizations run their core business on a vendor's system: a database they can read, whose schema, release cycle and API belong to someone else. Everything else grows around it. Tools query it directly, keep private copies that drift, and carry the vendor's quirks into every one of them.

This paper describes ORCA, an architectural pattern for that situation: own a translated, live copy for reads, and send every write back through the vendor. ORCA is assembled from known ideas. What it adds is how they are held together when the source is someone else's, and an exact account of which guarantees survive. It closes with what one implementation learned in production.

1The problem

Many organizations run their core business on a vendor's system: a practice-management, ERP or line-of-business product whose database you can read but whose schema, release cycle and API belong to someone else. Over the years everything else grows around it.

  • Direct reads. Dozens of internal tools query the vendor's database directly, each with its own polling loop.
  • Private copies. Each tool keeps its own partial copy, drifting slightly differently.
  • Leaking quirks. The vendor's model (packed flag bytes, coded columns that need lookups, one table doing several jobs) leaks into every one of them.
  • Slow, incomplete API. It is too slow and too incomplete to build on, and changing it is not an option.

ORCA is the shape that remains: own a translated, live copy for reads, and send every write back through the vendor. It is not a stack. Any language, database or message bus can implement it.

3The pattern

3.1Change capture

A low-latency, best-effort signal of which records changed, taken from outside the vendor's schema. Examples are a database trace session, a transaction-log reader, or network capture of the vendor's client traffic.

The obvious choiceTrust capture, as a change data capture pipeline usually does.Why ORCA doesn'tCapture taken from outside the schema is best-effort. Truth comes from a committed-only re-read.
  • Hints, not facts. A capture record says "look at this table, these keys". It never says what the new values are. It may arrive before the change commits, may describe a change that later rolls back, and may be missing entirely.
  • Resumable, with gaps marked. The stream has a position. A consumer reconnects from its last position and is told explicitly when records may have been lost (a gap).

3.2Operational store

Your own full copy of the vendor's data, kept current.

  • First copy. Resumable and paced, in key order, so the vendor's system never feels it.
  • Re-read on every hint. The touched rows are re-read from the source by primary key, with a read that only sees committed data. A rolled-back change re-reads as the original. The hint only decides where to look; the source decides what is true.
The hint only decides where to look; the source decides what is true.3.2 Operational store
The obvious choiceTrust the stream to keep the copy right.Why ORCA doesn'tCapture misses changes, such as trigger writes and unparsable statements. Only a comparison against the source finds them.
  • Reconciliation. Checksums compared by key range, re-copying only ranges that differ. It runs after every gap, as soon as each table's first copy finishes, and on a slow schedule. Reconciliation always wins over the copy and over the stream.
  • A raw layer. The vendor's tables kept exactly as they are, so translations can be rebuilt without touching the vendor again.

3.3Anti-corruption layer

A translation library that turns the vendor's model into yours: decoding packed values, resolving codes, splitting tables that do several jobs, and joining what always belongs together.

The obvious choiceTranslate at the boundary, inside the service that reads the vendor.Why ORCA doesn'tClients' fallback reads the source directly too. A library with no I/O, shared by both, gives the vendor's model one home.
  • Source-agnostic. It takes plain rows and returns your shapes, so it doesn't care whether the rows came from your store or straight from the vendor.
  • One copy of the vendor's quirks. Everything else in the platform only sees your model.

3.4Read models

Screen-shaped documents built by the translation layer from the raw layer, such as an order header, a notes log or a list row.

  • Versioned in commit order. Each change gets a version, and version order must equal commit order. A plain sequence is not enough, because sequence values are handed out before commit. A single counter row updated inside each shaping transaction serializes them.
  • Outbox. Each shaping transaction also writes its changes to an outbox table: the durable record every delivery reads from.
  • Whole versions only. One version can cover several read models. Delivery never splits a version, and a consumer applies a whole version and only then saves its position.

4Delivery, clients and writes

4.1Delivery

A fan-out layer (a pub/sub cache, a websocket service) carries committed versions from the outbox to everyone listening. It is delivery only, never the record: anything it loses is recovered from the outbox by position.

4.2Clients

  • Local cache. Clients can keep their own embedded copy of the read models they need (for example open records plus a recent window), fed by the delivery layer and resumed by version.
  • Fallback. When the platform is unavailable, a client may run the same translation library directly against the source. That fallback must be narrow (the one record on screen, rate-limited, clearly marked as live) so an outage of your platform never becomes a flood of reads on the vendor's.

4.3Writes

Nothing writes to the vendor's database directly. Every write goes through the vendor's own API.

The obvious choiceWrite to your own store, as CQRS assumes you own the write side.Why ORCA doesn'tYou don't. Writes go through the vendor's API and are judged by what comes back.
  • Intents first. A client records the user's intent in a durable local log, shows it at once, and can offer a short undo window.
  • One claimer per intent. A queue (e.g. FOR UPDATE SKIP LOCKED) ensures each intent has one claimer, in order per record. That is not exactly-once delivery: a worker can send and then crash before recording it.
The obvious choiceAim for exactly-once delivery, with idempotent retries.Why ORCA doesn'tA worker can send and then crash before recording it. ORCA replaces that with honesty: one claimer, never resend blind, and three outcomes.
  • Never resend blind. An uncertain outcome is resolved by observation, never by sending again.
  • Judged by what comes back. A write is judged by what returns through change capture, with three outcomes. Confirmed tied to this operation; for a create, the API returns the new record's ID and that exact record arrives. State reached the record holds the values sent, after the intent was sent, but nothing proves this request caused it; enough for plain "set this field" changes. Undetermined the evidence cannot tell; never retried automatically, shown to the person. Anything with side effects (creating records, sending, billing) only counts when Confirmed.
  • Leases with fencing tokens coordinate your own writers. They are checked when an intent is queued and again before it is sent. They cannot recall a request already in flight, and they mean nothing to people working directly in the vendor's application. Conflicts with those people are detected afterwards through capture, not prevented. The vendor's own record locks, if visible, are mirrored in as a warning.

5Guarantees

ORCA guarantees

  • Every committed source change eventually appears in the store (reconciliation).
  • The store never keeps a rolled-back value past the next re-read or reconciliation.
  • Version order equals commit order; no consumer skips a committed version.
  • A write is only reported done with evidence, and side-effecting writes only when Confirmed.
  • The vendor's model never leaks past the translation layer.

ORCA does not guarantee

  • That every change is seen through capture.
  • That reads are as fresh as the source at every instant.
  • Exactly-once delivery of writes to the vendor.
  • That a write's cause can always be proved (Undetermined exists).
  • Coordination with people using the vendor's application directly.

7A worked example

One order, followed through the system. "Order 42" is any record in the vendor's database. First the ordinary path, then the same order when things go wrong.

The ordinary path.State reached

The user sees the change at once, from their own intent log. The vendor's API applies it. Capture says only "orders, key 42". The store re-reads that one row with a committed-only read, rebuilds the read models for order 42 in one transaction that takes version 1001 and writes it to the outbox, and every client receives version 1001 as a whole. The intent compares what came back with what it sent: the values match and arrived after the intent was sent, so it is judged "state reached". For a create, the API's returned ID would make it "confirmed".

  1. Userrecords the intent and shows it at once
  2. User→Write queueenqueues it; the lease is checked
  3. Write queue→Vendor APIsends it; the lease is checked again
  4. Vendor API→Source databaseupdates order 42
  5. Source database→Change capturestatement completed
  6. Change capture→Storehint: orders, key 42
  7. Store→Source databasere-reads order 42, committed only
  8. Storerebuilds order 42's read models as version 1001
  9. Store→Userversion 1001, delivered whole
  10. state reached (a create would be confirmed by its ID)
Capture loses the event.

Nothing arrives for order 42. The intent waits; after its timeout the store re-reads order 42 directly, and the next checksum sweep would find the range anyway. The intent then resolves on what it sees, never by sending again.

  1. Write queue→Vendor APIsends the intent
  2. Vendor API→Source databaseupdates order 42
  3. Source database→Change capturestatement completed: the event is lost
  4. Usertimeout: nothing has come back
  5. Store→Source databasere-reads order 42 for the intent
  6. Store→Userchanged: version 1001
  7. resolved by observation, never resent
The change rolls back.Undetermined

Capture still reports "orders, key 42", because the statement ran. The committed-only re-read returns the old values, nothing changes, and no version is issued. The intent sees its values never arrived and ends "undetermined", shown to the user.

  1. Vendor API→Source databaseupdates order 42
  2. Source database→Change capturestatement completed
  3. Source databasethe transaction rolls back
  4. Change capture→Storehint: orders, key 42
  5. Store→Source databasere-reads order 42, committed only
  6. Storeunchanged: no new version
  7. values never arrived: undetermined, shown to the user
The sending worker crashes after the API call.

Another worker claims the intent. Its outcome is uncertain, so it checks the store before doing anything. Order 42 already shows the change, so the intent is judged on that, and the vendor is never called twice.

  1. Worker A→Vendor APIsends the intent
  2. Vendor API→Source databaseupdates order 42
  3. Worker Acrashes before recording the send
  4. Worker Bclaims the intent: outcome uncertain
  5. Worker B→Storechecks order 42 first
  6. Store→Worker Balready holds the change
  7. judged on what the store shows; the API is never called twice
Someone edits order 42 in the vendor's own application at the same moment.

Their change arrives through capture like any other. If it set the same values, the intent can only say "state reached", because nothing proves which request caused it. If it set different values, the intent ends "undetermined" and the user sees the conflict.

  1. Write queue→Vendor APIsends status = shipped
  2. Vendor app user→Source databaseedits order 42 directly
  3. Vendor API→Source databaseupdates order 42
  4. Change capture→Storeboth changes captured and re-read
  5. Store→Userthe latest version of order 42
  6. same values: state reached; different: undetermined
A client was offline overnight.

It reconnects from its last version. If the outbox still holds everything after that version, it receives whole versions in order; if not, it resynchronizes its read models instead of replaying.

  1. Clientcomes back, last saw version 1001
  2. Client→Storeresume after version 1001
  3. Store→Clientoutbox still holds it: 1002 onward, whole versions, in order
  4. Store→Clientor, too old: resync the read models instead of replaying
  5. resumed in order, or resynced; never a partial version

8Related patterns

ORCA is assembled from known ideas. What it adds is how they are held together when the source is someone else's.

Table 3. What ORCA takes from each pattern, and what it changes.

PatternWhat ORCA takesWhat ORCA changes
Change data capture6A stream of what changed, consumed from a positionCapture is only a hint; truth comes from a committed-only re-read, and gaps are expected and reconciled. No log access or schema change is needed.
Operational data storeA live, current copy for readsA raw layer kept exactly as the source, so translations rebuild without touching the vendor
Anti-corruption layer1Translate the outside model at the boundaryThe translator is a library with no I/O, shared by the store and by clients' direct-to-source fallback, so the vendor's model has one home
CQRS read models2,3Read-shaped data, separate from where writes goWrites don't go to your store at all: they go through the vendor's API and are judged by what comes back
Transactional outbox4Durable record of changes, written with the dataVersions are in commit order through a counter row, and delivered as whole groups so a consumer cannot skip part of one
Idempotent receivers, exactly-once6Avoiding duplicate effectsReplaced by honesty: one claimer, never resend blind, and three outcomes (confirmed, state reached, undetermined)
Leases with fencing tokens5Coordinating concurrent writersChecked at enqueue and before send; explicitly not a guarantee against requests already in flight or people in the vendor's own application

9When ORCA fits

It fits when

  • many tools depend on a system you do not control;
  • reads vastly outnumber writes;
  • the vendor's model is awkward;
  • the vendor's API is incomplete;
  • you cannot or will not alter the vendor's schema.

It doesn't fit

  • if you own the source (use its own change tracking and build read models directly);
  • if a few direct queries are enough;
  • if every write needs synchronous confirmation from the vendor in the user's path.

10In practice

One implementation, built against a vendor's practice-management system on SQL Server. Capture is an Extended Events session filtered to insert, update and delete, read by a small service next to the database. The store and read models are a Rust service with PostgreSQL. Delivery is Redis; clients keep LMDB caches. Any equivalent works: log-based capture such as Debezium, another database, Kafka for delivery, or SQLite on clients.

Running it taught several things the pattern does not say.

  • Capture catches every writer. Taken from the database server itself, it sees the vendor's desktop clients, its API, its web portal and its scheduled jobs alike.
  • A failing chunk is retried at half the size, down to one row, growing back after each chunk that works. A table that keeps failing is set aside for a few minutes while the others go on.
  • Sweeps cost the source the most, so they wait for off-hours. In working hours only small tables, and tables a capture record named, are swept. Nothing is dropped; the rest waits for the evening window.
  • A row is only deleted after a second lookup. The two databases don't order or compare text in exactly the same way. A copy row missing from a range is deleted only once a lookup by its primary key confirms the source no longer has it.
  • An older read can never land after a newer one. A re-read and a reconciliation of the same table each hold a lock on that table from their source read to their commit.
  • A schema change restarts the service. Every few minutes it compares the source's tables, columns, types and keys. On a change it exits and is restarted, and any table whose shape changed is copied again from the start.
  • Not everything is worth copying. One column of stored documents is left out of the copy and fetched from the vendor when someone opens one.
  • The translation is checked against the vendor every night. Random records are built from the copy and compared with the results of the vendor application's own queries. A record that differs is read again a moment later, and counts only if it still differs.
  • Freshness is measured, not assumed. For every change that reaches the read models, the time from capture to the commit of its rebuild is recorded, and the median and 95th percentile are logged every quarter hour.

11Conclusion

The combination is the point. A CDC pipeline usually assumes trustworthy capture and owned targets. CQRS usually assumes you own the write side. ORCA assumes neither, and says exactly which guarantees survive.
